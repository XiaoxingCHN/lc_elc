# 仓库公网访问安全与自有前端统一方案

日期：2026-10-26。状态：**方案待确认，尚未实施公网开放或旧入口停用**。

## 1. 目标与本次决策

用户从外网通过域名访问仓库，只使用现有Odoo账号登录一次。bore负责连接公网入口与内网服务器；HTTPS、入口收敛和Odoo权限负责安全。日常业务页面统一为我们的UI，不增加Cloudflare Access、第三方SSO、额外账号密码或客户端门禁。

官网`l-creation.club`继续由Netlify托管；仓库正式地址目标为`https://team.l-creation.club`。数据库、附件、库存和权限继续由项目Odoo实例维护。Web、Flutter、EDA共用既有业务模型，避免重复编写库存逻辑。

“只留自己的前端”分三层落实：

1. **普通用户看到的页面**：全部切到自有UI，不再出现Odoo菜单、原生表单或网站编辑器。
2. **公网可访问的路径**：只允许列明的自有页面、认证端点、业务接口和必要资源；其余默认拒绝。
3. **运维能力**：Odoo核心Web框架与必要视图代码保留；原生后台只能从独立的内网/VPN维护入口进入，且服务器校验系统管理员角色，仍用Odoo账号。维护入口不经bore转发；普通成员即使在内网也不能借旧Host进入原生WebClient。

本轮只形成方案。配置公网入口、切换DNS、升级模块或卸载旧网站须在实施任务中按确认范围执行；不会因本方案自动清库或卸载模块。

## 3. 公网连接方式与免费约束

### 3.1 采用bore，但区分验证环境和正式环境

bore提供的是中转服务器的**IP与端口**，不是为实验室分配独占公网IP。公共`bore.pub`默认分配端口，也可申请某个可用端口；DNS不能把普通HTTPS的443自动变成另一个TCP端口。

| 方式 | 成本与条件 | 用途 |
|---|---|---|
| 公共bore节点 | 可做零新增费用验证；端口、线路、稳定性、运营规则和来源IP能力待确认 | 先连接无生产数据的隔离环境；不能承诺正式服务质量 |
| 已有可控制的公网服务器 | bore及Nginx开源，不新增许可证费用；主机与带宽需已有资源 | 正式方案首选，能控制443、转发范围和真实IP |
| 新租公网服务器 | 产生主机/带宽费用 | 不默认采用；不符合当前零新增费用偏好 |

**免费软件、标准443、受控公网节点、稳定国内带宽不是同一项权益。** 若没有可控制的公网节点，先验证免费节点是否满足条件；不满足时保留内网入口，并把具体缺口交用户决定，不擅自购买或换服务。

### 3.2 正式方案的连接链路

受控公网入口进行TCP转发，不解密业务HTTPS；实验室Nginx持有证书并终止TLS：

```text
浏览器 / Flutter / EDA
  → team.l-creation.club:443
  → 公网Nginx stream：TCP转发，附加可信PROXY协议来源信息
  → 公网bore隧道监听端口（仅回环可达）
  → bore隧道 → 实验室bore客户端
  → 实验室专用Nginx公网应用监听器（仅回环可达）
  → Odoo本机业务端口 → 既有数据库及filestore
```

这里的额外Nginx是网络转发层，不增加登录页面。证书私钥仅保存在实验室。bore自身的隧道认证密钥用于限制谁能建立隧道，与仓库用户登录无关，使用受控私有配置，不出现在脚本参数、日志或Git中。

具体公网/本地监听端口、Nginx stream/realip模块、bore绑定参数、服务账号和systemd约束在环境核验后确定，避免与现有服务冲突。不给bore不必要的root权限，不在本任务改Docker、NAS默认路由或其他业务网络。

### 3.3 必须解决真实访客IP

官方bore为L4 TCP转发，当前不能假定它自动注入HTTP访客IP。官方Odoo19源码的登录失败计数实际以`remote_addr`为键，且计数不跨worker共享。若所有请求都变成回环/中转地址，会出现全体用户共用限速、日志无法区分来源等问题。

采用已有Nginx PROXY协议能力解决：受控公网TCP入口先加PROXY前缀，经bore原样传输，由实验室**独立监听器**解析；在该监听器只信任实际bore连接来源，并覆盖向Odoo发送的转发头。现有内网HTTPS监听器不要求PROXY协议，避免正常内网访问被破坏。

不得把客户端自己提供的`X-Forwarded-For`当可信来源，也不得对全局设置`set_real_ip_from 0.0.0.0/0`。同一监听器不混用带/不带PROXY的数据流。必须测试伪造头、两个真实来源IP、登录失败冷却及正常用户不被连带封禁。

这是待隔离验证的组合方案，不表示bore已经原生支持PROXY。若公共节点不可改造或测试无法恢复可信IP，停止正式公网开放；不自造隧道协议，也不通过关闭Odoo登录保护来掩盖问题。

### 3.4 域名、端口与内外访问

- 先保留现有内网/VPN入口；无数据的隧道验证可以使用临时域名/证书或明确端口，但不能忽略证书错误。
- 如只能取得公网高位端口，地址必须写成`https://<验证域名>:<端口>`；Host、回跳、资源、WebSocket、客户端Base URL和允许Origin都要包含正确端口。`$host`可能丢失端口，不能照抄当前仅内网443的代理配置。
- 正式无端口地址依赖公网443可用及DNS指向对应入口。DNS切换前，固定主机名/端口验证TLS、登录与路由。
- 所有客户端公网Base URL和认证请求必须直接使用HTTPS；若提供80入口，只对GET/HEAD做跳转，拒绝明文认证/写操作POST，不能把收到密码后再308当成首次传输已加密。
- 若同一正式域名的内网访问也要求直达实验室，需要路由器或现有DNS/VPN提供分流解析；不自动重新启动已停用的dnsmasq。若没有分流条件，记录内网走公网中转的性能与离线限制，再决定是否切换。
- 公网受控监听器固定仓库Host并拒绝其他Host/未知站点；修改Host不能落到旧官网、原生后台或别的数据库。官网Netlify记录保持原用途，不迁移官网托管。

## 5. 公网路由与旧入口整合

### 5.1 规则原则

采用单独的公网应用监听器，**默认拒绝**，逐项列出允许的路径及HTTP方法；不把当前`location /`通用代理直接暴露公网。URL是页面还是API由处理行为决定，不能看到`/web`就全部删除，也不能看到`/lab/api`就全部放行。

| 路径 | 正式公网策略 | 内网/过渡策略 |
|---|---|---|
| `/`、`/login`、`/lab`及已完成自有页面 | GET/HEAD；业务页面要求会话和对应角色 | 同一套自有UI |
| `/logout` | POST＋CSRF；不提供GET退出 | 同上 |
| `/lab_team_web/static/` | 仅该模块公开静态文件GET/HEAD；禁目录索引 | 不放行任意Odoo模块目录 |
| `/web/session/authenticate` | 精确POST白名单；同一个Odoo账号；清除`X-Odoo-Database`，限制可选DB并验证会话落盘 | 不新增登录系统 |
| `/web/session/get_session_info`、`/web/session/destroy` | 按已发布客户端需求精确POST白名单；检查失败响应及会话安全 | 保持Flutter/EDA兼容 |
| `/api/team/session` | 精确POST，自有会话/权限信息 | `/team/api/session`过渡兼容 |
| `/lab/api/catalog/search`、`detail`、`categories`、`facets` | 精确POST；目录角色校验，限制分页/查询开销 | 已有控制器复用 |
| `/lab/api/asset` | GET；已登录＋来源域/类型/大小/IP校验 | 不作为任意URL转发器 |
| `/lab/api/inventory/*`、写入/绑定/标签API | 从下一节清单选取**精确端点**；对应页面、权限和安全测试通过后分批开放 | 不使用整个前缀放行 |
| `/lab/client/updates/manifest` | 明确保留匿名GET签名清单，限platform/arch/channel | 不能一刀切要求登录而破坏启动检查 |
| `/lab/client/updates/assets/<release>/<file>` | GET/HEAD，实验室角色，发布包身份与路径边界校验，支持必要下载续传 | 不开放服务器目录 |
| `/web/image`、`/web/content`、`/report/*` | 默认拒绝；证明某资源必需后以受控资源接口或最窄路由替代 | EDA已有`/web/image`兼容逻辑，迁移前必须核对 |
| `/web/dataset/*`、通用`/jsonrpc`、`/xmlrpc*` | 默认拒绝，业务改走项目窄接口 | Flutter旧调用未迁移前保留内网兼容，不放开公网兜底 |
| `/web/database/*`、数据库选择/管理 | 公网拒绝；不向用户提供选库界面 | 数据库备份/恢复由受控运维完成 |
| `/odoo`及`/odoo/*`、原生`/web`入口 | 公网拒绝，不通过“登录后即可访问”放行 | 管理员独立内网维护入口保留 |
| `/website/*`、编辑器、原官网页面 | 公网拒绝 | 官网仍走Netlify；旧网站退役另做依赖审计 |
| `/team/*`旧页面 | 只列明已有GET页面的迁移映射；重定向至对应自有页面并保留安全next | POST不做盲重定向或重放 |
| `/lab/scan/resolve`、`/lab/scan/submit`旧表单端点 | 新扫码UI改用受控JSON-RPC后关闭公网访问 | 新流程验证前只内网兼容 |

## 6. Odoo与应用安全加固

### 6.1 账号、数据库和权限

- 保留Odoo原生密码哈希、会话与角色，不新增第二个身份系统。账号不共享；检查弱密码与长期不用的管理员账号。强密码在用户正常设置流程处理，不索取密码或直接改数据库字段。
- 核对项目实例数据库列表，仅记录名称和用途等必要元数据。确认是否还有其他业务/测试库，再选择该实例适用的`db_name`、`dbfilter`和`list_db=False`；不得为了单库入口删除未知数据库，也不把请求头固定库等同于认证body已限定库。
- 匿名、已登录无角色、目录用户、操作员、库存管理员分别验收；借用人从系统账号取，不能用客户端传来的操作人替换会话用户。
- 公网不开放自助注册/任意角色分配；管理员在内网维护账号与找回流程，仓库管理员不能借自有设置页提升为系统管理员。本人改密沿用Odoo的密码校验与安全机制，不明文存储或直接SQL更新。
- 领用、归还、袋移动、标签、建档绑定检查模型级权限、记录规则和必要的sudo边界；异常全部回滚，重复请求按request_key幂等。

### 6.2 登录限速与会话

- 先恢复可信来源IP，再配置Nginx登录精确端点限速与连接上限；原生Odoo冷却保留。具体阈值基于战队并发测量，不把全体用户共用的回环IP当访客。
- 原生冷却计数不跨worker共享，不把它视为唯一防暴力破解措施。需要账号级共享失败计数时先调研兼容Odoo19的成熟实现，做最小适配并独立审查，不复制密码认证代码。
- 不新增永久锁号或对整个隧道IP封禁的策略，避免攻击者轻易锁死全部正常成员。错误提示不区分“账号不存在”和“密码错误”。
- 认证成功、刷新保持、退出立即失效、会话过期、登录回跳和多账号切换均测试；保留冷会话补修，不再次让原生认证进入stateless模式。
- 核验session Cookie的HttpOnly/Secure/SameSite及作用域；Web不把密码或session_id放localStorage或URL。Flutter和本机桥接继续使用原有安全存储边界；十天无成功登录重新输密码的客户端约定保留。

### 6.3 请求、资源与服务器

- 精确方法白名单；GET不进行库存或配置写入。JSON-RPC要求正确JSON格式和Content-Type；浏览器敏感请求核验允许的Origin，限制跨域Cookie请求。原生客户端可能不发送Origin，不能通过无条件拒绝缺失Origin破坏App；需同时测试浏览器CSRF与客户端兼容。
- CORS不使用带凭据的全来源放行。`next`继续防开放重定向，输出文本转义；图片代理继续白名单域、私网IP拒绝、连接IP固定、无重定向及内容类型/大小限制。
- 自有页面设适合现有脚本的CSP、nosniff和防嵌入策略；不在仓库启用网站编辑器iframe白名单。敏感页/API不进入共享缓存。HSTS在续期与HTTPS稳定后按该Host逐步启用，不直接给整域加includeSubDomains/preload。
- 库存写接口与标签PDF限制请求体、批量数、分页、耗时；统一中文错误＋关联ID，不把原始SQL、路径、Traceback或含载荷的异常返回公网。
- 原生会话端点的非法DB/错误认证异常也检查完整响应体；若含调试堆栈，采用经审查的最小异常呈现适配，保留标准JSON-RPC兼容性，不更改密码验证逻辑，不能只在前端藏掉错误文本。
- 公网只到项目入口；SSH、数据库、原生Odoo端口和维护入口不经bore暴露。项目服务隔离/出站范围审查单独记录，不能未经授权改NAS全局防火墙或其他业务。
- 公网节点限并发/连接速率，应用入口限请求资源；免费中转不提供抗大流量DDoS的保证。WAF仅作为有实际攻击证据后的可选增强，不增加第二套登录，也不作为缺失权限检查的替代。
- 核对Odoo19补丁、Python/Nginx依赖和安装来源；证书DNS续期优先复用现成ACME客户端与阿里云最小授权，凭据只在受控私有位置保存，不在聊天/代码中传递；续期成功加载证书，失败报警。

4. 普通入口收敛验收后，观察旧客户端调用并确定兼容窗口；维护入口只限内网/VPN管理员，不为它注册公网通道。
5. 网站模块物理卸载作为独立可回滚任务：备份DB＋filestore＋代码，克隆隔离库，列出反向依赖、网站页面/附件/访问规则，演练卸载，验证自有页、登录、API、打印、客户端和库存计数。

最终普通使用体验只有自有UI；这通过入口、页面、链接、权限共同实现，不靠直接删除核心目录。

## 8. 实施阶段与责任分工

Codex负责方案/关键决策/验收；DSH在用户确认后沿用原项目与session实施，可以按已授权范围拆子任务。不同任务目录及验收边界明确，禁止多个代理覆盖同一文件。此文档不立即触发派发。

| 阶段 | 交付 | 放行条件 |
|---|---|---|
| P0 盘点与恢复交接 | HTTPS最终备份审计、DB/模块/路由/调用清单、可用公网节点与端口情况 | 生产状态和已有备份可解释；不把节点可连接当安全通过 |
| P1 隔离公网入口 | 无生产数据的bore链路、TLS透传、PROXY可信IP、Host/方法/路径白名单、限速实验 | 非仓库路径/伪造头拒绝，两个来源不互相误封，断隧道失败关闭 |
| P2 只读自有UI试运行 | 登录、目录、详情及必要资源/会话/更新API | 不增加登录；冷会话/退出/角色/跨来源/设备兼容通过；才允许有限生产试运行 |
| P3 写业务UI | 两阶段入库、领用归还、袋追溯、库位映射、标签和管理页 | 隔离真实ORM/并发/幂等/权限与人工业务验收通过，分批开放端点 |
| P4 全入口统一 | EDA跳转与Flutter调用迁移、旧页迁移/拒绝、正式DNS切换 | 普通用户全部业务无需旧UI，内外登录与资源/回跳正常 |
| P5 旧网站退役 | 网站依赖审计及隔离卸载报告、可选生产卸载 | 用户确认实际模块清单和影响；不因只用仓库而清库 |
| P6 运维收尾 | 自动续期、日志告警、恢复演练、版本/源/产物登记和交接 | 证据齐全、未测项明确、按确认范围发布 |

公网节点选型及真实IP问题可以与自有UI开发分别推进；节点不合格不妨碍内网完善UI。实施时每个阶段新建任务单、冻结相应组件源；变更模块版本与客户端版本分别管理。

性能可先以“失败/超时率低于1%、常用搜索p95不超过3秒”作为候选目标，再按真实规模确认。这是设计目标，不是已有测速或对免费节点的服务承诺。首轮只少量自愿成员；未完成写操作验收时公网只读。

上线前完成项目相关备份路径/哈希与恢复方案核验；模块升级与证书/代理操作分别记录退出码。生产不创建测试用户、不写测试库存、不伪造会话；功能写入在隔离库用合成账号验证，生产真实登录由用户自行操作。

## 10. 回滚、成本与待确认事项

- 网络故障：停止本项目bore客户端/公网专用映射，恢复本次DNS记录，保留内网/vpn入口；不重启NAS网络或恢复旧DNS服务器。
- 代理故障：恢复已校验备份中的项目vhost，`nginx -t`后reload；不覆盖其他vhost或数据库。
- UI/API故障：按源manifest及模块升级方案回退，优先前向兼容；真实业务数据继续保留，不用整库旧备份抹掉已发生库存。
- 网站卸载故障：仅在已批准的独立窗口按完整备份恢复，明确停机和新增业务写入边界；未准备恢复演练则不卸载。
- 开源软件无许可证订阅费，不等于中转主机、带宽、运维和可靠性没有成本。优先已有可信公网资源；第三方公共节点只在其规则允许和测试合格的范围使用。

实施前需确认的具体事项：

1. 是否已有可控制的免费公网节点，能否使用443并配置Nginx stream/PROXY？没有则先按免费公共节点的实际能力做隔离测试，不承诺无端口正式域名。
2. 是否接受保留“管理员仅内网可达”的原生维护入口？本方案推荐保留；普通用户仍只使用自有UI。
3. 实际成员与并发、外网先只读还是完成P3后才一起上线？本方案推荐先只读小范围试运行。
4. 回内网后核对HTTPS收尾审计、证书自动续期和实际网站依赖；在这些事实确认前不关闭当前可用入口。
