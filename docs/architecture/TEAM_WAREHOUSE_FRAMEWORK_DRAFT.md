## 三条日常主流程

采购入库准备循环：选择或新建器件 → 填每袋数量/袋数 → 为每袋生成唯一追溯码 → 放入待打印 → 继续添加。制袋/打印不改变真实库存。保留待打印状态、失败提示和重新进入恢复能力。

采购入库上架循环：扫袋码 → 显示器件/数量 → 推荐同类优先库位 → 扫描或选择库位 → 确认入库 → 扫下一袋。仅确认上架后由服务端执行真实库存移动；重复确认不得重复入库。

领用与归还：选择器件和真实袋/库位 → 选择系统账号领用人、项目、数量 → 校验后领用；归还必须选择原领用记录并校验未归还余额。扫码与手工查找进入同一套业务状态，不能各自实现不同记账。

新增独立的战队Web入口模块/应用外壳，复用现有JS/OWL能力与业务接口，但自行管理布局和路由，不在Odoo原生后台里换一层CSS。具体挂载与服务依赖先做隔离验证，验证失败再选替代方案，不凭草图承诺已实现。

- lab_workflow：两阶段入库、袋码、领用归还、追溯、标签、幂等与并发校验。
- lab_inventory及stock/product：器件与库位基础信息、真实库存底座。
- lab_theme/lab_site：现有后台主题/网站兼容保留，不作为新仓库前端的必需壳；待新流程验收后再评估收敛与卸载影响。

## 服务端先做什么

先盘点已有接口与权限，不为每个菜单重复造接口。现有网页直接receipt与Flutter pending两阶段流程不一致；新网页统一走两阶段入库。确认会话状态/可用功能、器件详情与袋/库位、领用归还与历史查询的完整契约，缺口再补。

服务端强制登录与角色、公司/记录权限、幂等request_key、数量/余额与并发校验；前端隐藏按钮不能代替权限。实验室库存只信stock.quant/stock.move。旧Flutter及EDA调用不破坏；新前端和Flutter复用相同业务规则，但不要求第一轮同时重写Flutter。
