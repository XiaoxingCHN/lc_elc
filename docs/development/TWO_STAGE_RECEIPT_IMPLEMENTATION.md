# 两阶段入库实现与验收

日期：2026-10-19。开发候选源：客户端 **1.1.0+3**、lab_workflow **19.0.1.1.0**。现成客户端包及已记录生产模块仍是归档版本，本轮没有发布或部署。

需求见[计划书](TWO_STAGE_RECEIPT_PLAN.md)。操作入口：登录后的仓库右下角“采购入库”，器件详情另有“制袋贴标”；原直接入库保持兼容。

## 操作与边界

1. “制袋贴标”：选择器件及明确的 SN 档案，或在底部表单新建无资料器件；填写每袋数量和袋数，生成独立袋码并保存服务器待打印选择。继续添加其他器件，进入标签页按毫米设置尺寸、预览 A4 PDF、打印和补打。
2. “扫码上架”：扫描待入库袋，显示型号、参数与数量；相同立创编号的已有库存库位优先，其次内部物料分类的同类库位。推荐需要操作者选择，也可手选或扫描库位码。核对对话框显示袋码、数量和库位，确认后提交实际库存并继续扫描。

待入库记录独立存储，不创建 stock.lot、stock.move 或可领用袋。确认通过原库存业务方法创建真实库存移动；同一事务标记已入库并关联正式袋。行锁、请求指纹、幂等回放与正式袋的 pending_receipt_id 唯一约束共同防重。两次独立确认请求只能对应同一个正式袋。

袋码另有统一的数据库唯一性登记，覆盖预留码和直接入库码，避免两个业务模型各自唯一却互相撞码。模块升级时只登记历史袋的既有码，不改历史库存或标签；登记不可删除、改写或循环使用。

同一袋在制袋和实际入库后使用相同 `LABB:` 二维码。补打不生成新袋；取消保留记录且禁止后续打印／确认。已入库袋再次扫描只显示结果，不重复入库。

待入库列表与打印选择只对创建账号的当前公司开放。新服务入口在模型层校验操作员权限；模型拒绝直接 RPC create/write/unlink，客户端 context 不能伪造内部写入能力。切换服务器、数据库、账号或公司会重建客户端页面并丢弃旧异步响应。业务数据不写公开离线缓存。

网络结果不确定时，客户端保留同一提交参数与请求号并锁定表单，重试取回原结果。明确的校验错误允许修改。退出重开后从服务器恢复记录与打印选择；未提交的本地输入草稿不持久化。

## 标签字段

默认：袋码文字、型号／名称、关键参数、封装、有则显示的立创编号，并始终仅有一个追溯二维码。品牌与内部 SN 可选；初始数量和库位默认关闭。数量字段明确叫“初始数量”，不表示当前余量。

电阻优先阻值、精度、功率；电容优先容量、耐压、介质等；其他类型取已有参数的前三项，完整参数仍在详情。缺失值不补造。待入库标签必须保留袋码文字。默认尺寸 60×40 mm，实际打印前仍需按纸张调整、预览；放不下则拒绝生成，不裁掉关键内容。

## 新 API 契约

均使用现有认证会话、POST JSON-RPC 和 `{ok,data,error}` 信封，权限由服务端决定。写入身份来自会话，不能指定其他 owner/company。

| 路由后缀（前缀 /lab/api/inventory） | 请求 | 返回 data |
|---|---|---|
| /pending/list | 可选 cursor（递减整数 ID） | records、下一页 cursor；每页最多 100 项 |
| /pending/create | request_key、quantity、count；item_key 与可选 product_template_id，或 material | records；每袋独立 ID 和码，同请求回放原结果 |
| /pending/update | pending_id、action=select 与 selected 布尔值；或 action=cancel | record |
| /pending/resolve | raw 袋码 | record、recommendations；历史正式袋返回 bag |
| /pending/confirm | request_key、pending_id、quantity、location_id | record、库存业务结果与 revision；重复确认返回原正式袋关联 |

`material` 允许 name、mpn、package、brand、specification，仅 name 必填；只创建本公司档案，不在建档时录入实际库存。选择已有器件时复用已绑定档案，多档案必须明确选择。

确认身份使用 `pending_id`，避免既有请求规范化将传输层 `id` 排除出指纹。标签预览沿用原路由，新增 `kind=pending`，ids 指待入库记录；服务端仍逐项检查归属。普通已入库袋和库位标签保持兼容。

路由注册表已重新生成至 maintenance/registry/routes.json，共 30 项；注册表不替代本节输入、权限与事务语义。

## 界面设计与审查

本轮应用 apple-ui-designer 和 apple-design，审查对象为 Flutter 源码、组件布局测试和真实组件截图；Windows/Android/Linux 采用 Apple 的清晰层级与可访问性原则，保留各端原生输入、PDF 和打印能力。

| 页面 | 设计意图、布局和文字 | 交互与理由 |
|---|---|---|
| 制袋贴标 | 单列分组表单，桌面最大内容宽 760；大标题、器件和数量优先，次要记录折叠隐藏；正文主要使用 17 px 的主题文字 | 两步骤切换；搜索器件与底部新建表单；主动作生成袋码，次动作管理记录与打印；逐项核对适合连续采购处理 |
| 扫码上架 | 扫码 → 器件与参数 → 数量 → 推荐与库位 → 确认；状态用文字表达；库位和数量均在确认时可核对 | 采用标准输入、菜单、对话框，无装饰动画；成功清空当前袋并恢复下一次扫码输入，超时重试锁定原请求 |
| 标签设计 | 下拉选择待入库袋／正式袋／库位，避免三个长分段标题挤压窄屏；默认精简稳定信息 | 复用原预览、导出和系统打印；切换类型重置对象，重入页面时同步显示真实尺寸配置 |

审查引用（来自技能内已读取的 HIG 资料）：

- `accessibility.md › Vision`：“Support larger text sizes.” 两种明暗主题、320 和 1280 宽度均做 200% 文字组件测试；大字体时步骤分段切换为菜单。
- `buttons.md › Best practices`：“a hit region of at least 44x44 pt”。新页面主按钮最小 44×48，文字按钮最小 44×44；控件保留默认按下、焦点与禁用反馈。
- `color.md › Platform considerations`：使用语义色区分背景、分组和文字，避免新页面继承硬编码白色输入底；状态和错误不单靠颜色。
- `typography.md › Using system fonts`：“Consider using the built-in text styles.” 沿用平台／主题字体和系统缩放，不打包 SF 字体。
- `layout.md`、`designing-for-ios.md › Best practices`、`entering-data.md`、`dark-mode.md` 与 `references/cross-platform.md` 用于布局、选择优于输入及框架翻译审查。

已修正：窄屏标签类型溢出风险、放大文字步骤标题、触控尺寸、确认时遗漏库位、标签类型跨页面残留、尺寸输入与内部状态不一致、隐藏已处理记录仍被计入打印选择。

设计结论：代码和组件范围内可继续验收；没有发现本轮未修正的阻断级设计问题。截图来自测试渲染，无法代替手机、桌面原生运行、屏幕阅读器或实体打印验收；未测量完整原生界面的颜色对比度，不据截图宣称全部 HIG 合规。截图位于 local/build/two-stage-ui（Git 排除）。

## 本轮验证与限制

详细结果、失败尝试和环境见[任务交接](../../maintenance/handoffs/2026-10-19-two-stage-receipt.md)。执行要点：

- Flutter 测试通过缓存中的 SDK 原生 Dart 运行 flutter_tools.snapshot，设置项目内 PUB_CACHE、临时目录和 FLUTTER_SUPPRESS_ANALYTICS=true；测试不调用生产接口。
- 组件用例覆盖创建与确认的响应丢失重试、手工档案复用、恢复队列、跨账号／公司迟到响应、明暗主题和文字缩放。
- Odoo 在既有只读运行时外创建全新的命名空间、私有 loopback 与临时 PostgreSQL 数据库。执行 run_isolation_tests.sh --keep --with-http --skip-process-concurrency --real-catalog 指定当前 addons 目录；子进程清除继承的代理环境，不修改全局代理。
- 实际 ORM 测试覆盖待入库无库存副作用、单次确认、PDF 生成、取消、直接 RPC 与预留码保护、指纹拒绝错袋，以及同料号跨档案推荐。
- HTTP 六项验证包含两设备同请求制袋、两设备不同请求确认同一袋，双方独立登录、实际事务相交。既有归还并发夹具改用同一借用账号的两个会话，避免把“他人无权归还”的拒绝当作数量并发验证。
- 进程内并发夹具出现测试框架锁等待，本轮中止该测试进程、保留失败日志，最终显式 skipped；不能用 HTTP 结果把该夹具标为通过。

本实现验收时未执行三端原生构建和安装升级、Android 相机／蓝牙扫码枪、Linux SecretService/CUPS、实际纸张扫码与打印、生产升级及回滚演练。后续已重建三端候选包，证据及仍未验收项见[原生候选交接](../../maintenance/handoffs/2026-10-19-native-candidates.md)；服务端进展见[上线交接](../../maintenance/handoffs/2026-10-19-server-deploy.md)。新源码冻结和测试通过均不代表已发布安装包。
