# 两阶段入库与袋标签计划书

日期：2026-10-19。状态：方案已形成，后续已完成候选源码实现，见[实现与验收](TWO_STAGE_RECEIPT_IMPLEMENTATION.md)。本计划不代表已发布安装包或完成生产部署。

## 目标与现状

让一次采购的多种器件先集中建档、生成袋码、打印贴标，再携实物逐袋扫码、选择库位、确认入库。每袋或每个实物批次有独立追溯码；同型号共用器件资料，一袋中的每颗元件不单独编号。

当前客户端的流程是选择器件、数量及库位后调用实际入库接口，服务端创建袋与库存移动，成功后才能打印袋标签。标签页没有已入库袋时会拒绝打印。因此本需求需要同时调整 Flutter 客户端与 Odoo 服务端，不能仅增加一个按钮。

现状依据：`clients/app/lib/features/unified/screens/labels_screen.dart`、`receipt_screen.dart`、`clients/app/lib/services/lab_api_client.dart`，以及 `server/ubuntu22.04/odoo_addons/lab_workflow/models/lab_workflow_api.py`。

## 两个操作循环

### 循环一：批量建档、准备标签

1. 搜索或选择器件；没有合适资料时进入建档流程，绑定已有资料时避免重复创建器件档案。
2. 填写每袋初始数量、袋数和必要备注；本期默认同一操作的各袋数量相同，不同数量分次添加。
3. 保存待入库记录，由服务端为每袋分配唯一袋码，绑定器件档案和待入库数量。
4. 加入待打印队列，显示型号、规格、袋码与数量供核对，继续添加下一种器件。
5. 按毫米设置标签尺寸、页边距、间距，预览 A4 排版并批量打印；逐袋核对实物后贴码。

待入库记录及打印选择支持退出后继续处理。同一批次重新打印沿用原袋码；新增一袋必须生成新袋码。“打印份数”仅表示同一码的副本，不代表新增实物袋。

打印或导出 PDF 不能证明实物已贴标，不以打印完成标记作为强制入库条件。支持取消尚未入库的记录；取消后二维码可查询取消状态，但不能继续入库。

### 循环二：扫码、推荐库位、确认入库

1. 扫描袋码，读取对应待入库记录、器件参数、待入库数量与状态。
2. 推荐有相同器件的已有内部库位，再考虑同类器件库位；推荐只作辅助，允许手选或扫描库位码。
3. 操作者核对数量与库位；如调整数量，保存最终确认值和修改记录。
4. 确认后在同一服务端事务内创建正式袋、批次和实际库存移动，将待入库记录关联至正式袋并标记已入库。
5. 显示入库结果，自动回到下一次扫描，支持查看上一袋结果和补打原标签。

只有第 4 步成功提交才增加库存。打印、扫描、推荐和取消待入库记录均不改变实际库存。已入库码再次扫描显示原结果和详情；不再执行第二次入库。

## 袋标签内容

| 字段 | 默认 | 说明 |
|---|---|---|
| 袋追溯二维码 | 必须 | 每张仅一个，编码为稳定袋身份，沿用 `LABB:` 体系；服务端解析资料，不把数量、库位当作二维码内的实时事实 |
| 袋码文字 | 显示 | 扫码失败时可手工输入，必须与二维码对应 |
| 型号／名称 | 显示 | 核对实物与标签 |
| 关键参数 | 显示 | 按器件类型选取，避免把全部供应商参数堆到小标签 |
| 封装 | 显示 | 如 0603、0805、SOT-23 |
| 立创编号 | 有则显示 | 非立创器件可为空 |
| 内部 SN、品牌 | 可选 | 与袋码区分，SN 标识器件档案，袋码标识具体实物袋 |
| 初始数量 | 默认关闭 | 开启时明确写“初始数量”，不表示当前库存余量 |
| 库位 | 本流程默认关闭 | 打印时尚未决定库位；库位另贴库位标签，当前库位通过扫码查询 |

参数示例：电阻选阻值、精度、功率；电容选容量、耐压，资料齐全且空间允许时增加介质。缺失数据不猜测。字段过多导致不可读时提示减少字段或增大标签，不能静默省略袋码或把二维码缩到不可扫描。

关键参数的具体分类映射和实际纸张扫码效果留在实施阶段验证。其他已有标签模式继续保留其字段配置能力。

## 数据、接口与权限方案

以下是建议实现方向，接口名称和字段在实施前结合现有 API 约定确定。

- 新增独立待入库记录，状态为“待入库、已入库、已取消”。打印是附属事件，不改变库存状态。
- 记录至少含器件档案、唯一袋码、初始／待入库数量、单位、创建人、时间、备注，以及确认后的数量、库位、操作人、时间和正式袋关联。
- 待入库记录不创建可领用库存，不计入库存卡片数量、袋可用数量或领用候选列表。
- 创建待入库记录时通过既有序列机制或统一分配器确保全局唯一；生成正式袋时使用同一码。分配、迁移与兼容策略须覆盖历史袋码，防止两个模型之间冲突。
- 提供创建／查询／取消待入库记录、读取标签、推荐库位和确认入库能力；扫码解析须同时识别历史正式袋和待入库记录，返回明确状态。
- 标签渲染允许读取待入库记录，确认入库前后保持二维码一致，沿用单 QR 和 A4 PDF 能力。
- 创建与确认均使用幂等键；确认时锁定待入库记录并复核状态、权限、公司、有效数量及内部库位。网络超时重试与双设备并发只能生成一次正式入库。
- 已确认记录不能再用“取消待入库”撤销；库存纠错走独立业务流程并保留审计。
- 服务端沿用业务权限校验，普通只读用户不能创建、取消或确认。离线仍仅允许读取公开缓存，不新增待入库或打印队列业务数据的离线缓存。
- 未打印选择保存在服务器或受会话隔离的现有业务存储中，不进入公开缓存；切换账号或公司时重新鉴权与加载。

库位推荐本期按“同器件 → 同类 → 手选”顺序。没有可靠容量数据时不承诺容量匹配或自动分仓，不强制同类存入同一库位。现有直接入库接口保持兼容，并与待入库确认共用库存业务规则。

## 界面调整

- 增加“待入库／制袋标签”入口，包含批量添加、待入库列表、打印选择、补打和取消。
- 添加完成后可“继续添加”或“查看待打印”，清楚区分新建袋数与同一码打印份数。
- 扫码页按状态显示操作：待入库可确认，已入库查看详情，已取消说明原因；历史正式袋继续可查询和补打。
- 实际入库前展示器件名称、关键参数、数量和目标库位；成功后继续扫描，失败时保留当前记录并支持安全重试。
- Windows、Android、Linux 使用同一份 Flutter 业务源码；按平台验证扫码输入、PDF 与原生打印差异。

## 实施顺序与范围

1. 梳理现有业务权限、扫码返回值、标签渲染及库存事务，确定接口契约与数据升级方案。

## 验收标准与验证计划

| 场景 | 通过条件 |
|---|---|
| 连续添加多种器件、同型号多袋 | 每袋独立码，档案正确关联；实际库存始终不变 |
| 关闭重开、切换账号 | 当前账号可继续处理；其他账号无越权读取或复用选择 |
| 批量预览、补打、取消 | A4 排版正确，每张单 QR；补打原码；取消不改变库存 |
| 标签内容 | 默认字段符合上表；缺失值不编造；数量注明初始；可读且可扫 |
| 扫待入库码 | 参数和数量正确；可推荐、手选或扫描库位，无库存副作用 |
| 确认入库 | 正式袋沿用原码，stock.move／stock.quant 正确，历史可追溯 |
| 重复扫码、超时重试、双设备并发 | 同一待入库记录只产生一次入库，能返回原结果 |
| 已取消码、无效码、越权请求 | 明确拒绝；无新增袋、批次或库存移动 |
| 历史正式袋及旧客户端 | 扫码、补打和既有直接入库接口继续工作 |
| 领用、归还与离线 | 待入库袋不可领用；正式袋原流程正常；离线仅公开资料只读 |
| 三端及实物打印 | 记录各端实际执行项、扫码方式、打印尺寸与设备，未执行项明确标 skipped／blocked |

实施阶段执行相关 Flutter 测试、服务端纯逻辑与独立 Odoo ORM 事务测试，并核验真实库存移动与权限；纯逻辑通过不能替代 ORM 验收。完成后执行仓库检查与差异检查。物理打印需验证中文、二维码、边距及实际尺寸，不仅检查 PDF 生成成功。

计划书形成阶段仅做文档检查；后续实现阶段的实际测试和未验证项见[实现与验收](TWO_STAGE_RECEIPT_IMPLEMENTATION.md)，不以本计划中的目标代替通过证据。
