## 二、方案（建议）

### S1. 统一扫码入口，按「码的类型」分支

新增 `/scan` 页（也复用到目录页 FAB）：扫到或键入任意码 → `resolve_code`：

- `LABL:`（仓位码）→ 弹出三项：**录入库存 / 查看该仓位内容 / 打印仓位标签**
- `LABB:`（袋码）→ 现有「扫码上架」核对（数量+库位确认）
- `C…`/SN/立创原厂码 → 现有「制袋贴标」并预选该器件

这样「扫描库存仓位二维码 → 是否录入库存」就落在第一个分支上，两条路径都不丢。

### S2. 新增「仓位内容」页 `/location/:id`

- 客户端补 `bags({locationId, cursor})`（服务端 `/lab/api/inventory/bags` 已支持
  `location_id`、`has_stock`、`next_cursor` 分页，无需改服务端）。
- 页面：仓位名/库码、合计袋数与数量、袋列表（袋码、器件、数量、SN），
  每行可跳详情；顶部三个动作：录入库存 / 打印仓位标签 / 刷新。
- 顺手把 `locations()` 加 `with_stats: true`，让列表能显示袋数（服务端已支持）。

### S3. 录库界面接受仓位上下文

`/receipt/prepare?location_id=…` 与 `/receipt?location_id=…`：进入时预填并**锁定**库位
（图上是从仓位进来的，不该再让操作员改到别的仓位；保留「更换库位」二次确认）。

### S4. 制袋改成「清单 → 一次提交」

- 表单里「生成袋码并加入待打印」改为**加入本次清单**（内存，不写服务端）：
  每行 = 器件 + 每袋数量 + 袋数 + 备注。
- 清单底部「确认录入系统并生成袋码打印」：一次性 `pending/create`（按行拆多次调用，
  每行独立 `request_key`），成功后直接进打印。
- 保留逐件立即生成的旧路径作为「立即制袋」次要按钮（失败重试语义不变）。

### S5. 立创候选 → 自定义器件

`CatalogFetchPanel` 的候选列表底部加「都不合适，自定义器件」，直接打开现有
`_NewMaterialSheet`，并把搜索关键词预填到型号/名称。

### S6. 仓位标签打印入口

- 仓位内容页 / 仓位列表页每行「打印仓位标签」→ `labelsForLocation(id)`。
- 标签内容按图 3：QR（`LABL:`）+ 仓位名称（当前 `fields: ['location','name']` 已是这个语义，
  只需确认标题用库码还是名称——图上写「仓位名称」，建议标题=库码、正文首行=名称，
  与现有去重逻辑一致）。

## 三、需要用户拍板的点

1. **扫仓位码是否成为唯一入库入口？** 建议保留目录页 FAB（新装/无标签时仍需能进），
   但把 FAB 改成打开 `/scan`，让两条路都从扫码开始。
2. **制袋是否改成「清单→一次提交」（S4）？** 这会让「生成袋码」从每件一次变成最后一次；
   失败重试的粒度也变成整批。若希望保留逐件即时反馈，可只做 S1/S2/S3/S5/S6，S4 缓做。
3. **「查看仓位内容」的权限**：`inventory/bags` 在 web 端是 lab 角色只读，客户端沿用同一角色即可。

## 四、风险与未验证

- S4 会改动制袋的失败语义与 `request_key` 生命周期，需重跑
  `test/features/unified/pending_receipt_test.dart` 与新增批量用例。
- 三张图未覆盖领料/归还，按「不动」处理。
