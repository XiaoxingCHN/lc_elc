# 事故记录：2026-10-27 原始 Odoo 端口意外暴露到公网

## 摘要

在验证 bore 公网接入可行性时，我在**生产服务器**上执行了 `./bore local 8069 --to bore.pub`，把原始 Odoo 端口 8069 直接暴露到公网 `bore.pub:62623`，绕过了 Nginx 的 CSP、路径白名单、Host 校验与认证网关。

随后清理时使用 `pkill -f 'bore-test/bore local'`，与实际进程命令行 `./bore local` 不匹配，**隧道继续运行约 13 分钟**。

- 暴露开始：2026-10-27 18:12:08（本地）
- 隧道实际终止：2026-10-27 18:25 之后（主代理发现并强制终止）
- 时长：约 13 分钟

## 根因

1. **在生产环境做可行性测试**：本应在隔离环境或本地验证，不应在承载真实数据的生产服务器上启动对外隧道。
2. **暴露了错误的端口**：应指向受 Nginx 保护的 443 入口，而非 8069 原始端口。
3. **清理未验证**：终止命令使用了不匹配的进程特征串，且未在终止后复查 `pgrep` 输出，导致误报"已清理"。

## 影响评估（基于实际日志）

暴露窗口内 Odoo 访问日志共 22 次请求，全部来自 `127.0.0.1`（bore 客户端转发，日志无法区分真实来源）。

请求清单：

- `GET /web/database/selector` 200 ×1
- `GET /web/login` 303 ×2
- `GET /` 303 ×1
- `GET /odoo` 303 ×1
- 其余 17 次为 `/web/static/*` 静态资源（bootstrap、fontawesome、logo）

**未发现**：

- 任何 POST 请求（无登录提交、无表单、无 API 调用）
- 数据库创建/删除/备份/恢复操作
- `/web/database/manager` 或 admin_passwd 相关访问

## 已泄露的信息

- **数据库名称**：`LcHardwareHouse`、`lc_hardware`（通过数据库选择页可见）
- Odoo 版本信息（19.0，可从静态资源路径推断）

未泄露：账号、密码、会话、库存数据、附件、配置。

## 处置

1. 强制终止 bore 进程（`pkill -9 -f "bore local"`），确认 `pgrep` 无输出
2. 删除 `/home/hbut/bore-test`（含二进制与日志）
3. 确认 62623 / 7835 无监听
4. 核实 Nginx 443 入口防护完整：`/lab` 仍返回 303，`/login` 返回 200
5. 核对数据、账号、附件无变更

## 建议后续

- 数据库名称已暴露，若在意可评估启用 `dbfilter` 与 `list_db=False`（当前配置仅有 admin_passwd，未见 dbfilter/list_db）
- 检查是否存在弱密码账号（6 个用户中非活动/模板账号应确认）
- 公网接入改用受控方案（国内公网节点 + 443），禁止再暴露原始端口

## 教训

- 生产环境不做"试试看"性质的网络暴露实验
- 任何对外暴露必须先确认目标端口是受保护入口
- 清理操作必须用结果验证（`pgrep`/`ss` 复查），不能只凭命令执行成功就宣称完成
